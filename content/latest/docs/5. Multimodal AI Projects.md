## 5.2 Voice-Controlled Dot Matrix Display

### 5.2.1 Lesson Introduction

This lesson focuses on voice-controlled dot matrix display projects with the Nexbit AI robot car, introducing the WonderLLM voice module and dot matrix command blocks. Issuing voice commands triggers the AI to call MCP tools, displaying numbers, text, icons, arrows, or clearing the dot matrix screen. Mastering the fundamental logic of AI tool calling lays the programming foundation for subsequent AI voice interaction projects.

### 5.2.2 Learning Objectives

1. **Knowledge Objectives**: Identify the micro:bit LED matrix display. Understand MCP tool-calling principles with WonderLLM, and recognize the full workflow from voice recognition to screen display.

2. **Skill Objectives**: Master adding the **nexbit** and **wonderllm s3** extension packages. Configure MCP display tools. Complete program upload and debugging to achieve a voice-controlled dot matrix display.

3. **Thinking Objectives**: Understand how multimodal AI models drive hardware interaction. Develop engineering thinking in parameter matching and troubleshooting.

4. **Application Objectives**: Master implementation methods for AI voice-controlled peripherals. Understand fundamental voice interaction applications in educational robotics.

- **MCP Configuration Analysis**

1. Tool name: `self.control.microbit_display`

2. Tool description: When you want to display numbers, characters, text, built-in icons or arrows on the micro:bit LED display screen, please use this tool. The parameter `display_type` must be one of `number`, `character`, `text`, `icon`, `arrow`, or `clear`. For numbers, `display_value` is the numerical value to be displayed. For characters or text, `display_value` is the scrolling content of the characters or text. For icons, `display_value` must be one of the following: `heart`, `small_heart`, `yes`, `no`, `happy`, `sad`, `confused`, `angry`, `asleep`, `surprised`, `silly`, `fabulous`, `meh`. For arrows, `display_value` must be one of the following: `north`, `northeast`, `east`, `southeast`, `south`, `southwest`, `west`, `northwest`. For `clear`, `display_value` can be empty.

3. Return parameters: `[["display_type", "string"], ["display_value", "string"]]`

4. Block until tool execution completes: `false`

5. Data returned to AI module: `false`

6. Function: This MCP tool enables the AI to call the micro:bit dot matrix display. It supports six display types. The AI automatically matches parameters based on voice commands to drive screen rendering.

**Project 1: Multi-Step Sequential Display Interaction**

Issuing the voice command "Auto demo" causes the dot matrix screen to sequentially display a heart, clear the screen after a 2-second delay, and display the number 3. Speaking the command "Stop" interrupts the demonstration at any time. This project practices continuous MCP tool calling and voice interrupt control programming.

This project practices adding MCP tools and understanding configuration workflows for multi-hardware cooperative control.

### 5.2.6 Q&A

**Question 1: What is MCP?**

Answer: MCP, also known as Model Context Protocol, is a tool-calling configuration mechanism. It defines hardware feature tools available to the AI module, specifying tool names, functional descriptions, and input parameter formats. This mechanism enables large language models to interpret voice commands and output parameters in an agreed format, allowing the underlying hardware to execute corresponding actions.

**Question 2: Why configure MCP?**

Answer: Large language models cannot directly manipulate hardware. Configuring MCP tools informs the AI module of available hardware features and parameter structures. This enables the AI to convert parsed voice semantics into executable command parameters recognized by the hardware, achieving AI voice control over physical devices.

**Question 3: What happens if MCP is not configured?**

Answer: Without MCP configuration, the AI module cannot identify available dot matrix display tools. It cannot parse voice commands or generate corresponding control parameters. Even if speech is recognized, the micro:bit dot matrix screen cannot be driven, preventing voice-controlled display features from functioning.

### 5.3.6 Q&A

**Question 1: With two sets of MCP tools configured in this project, can the AI invoke both tools simultaneously?**

Answer: Yes. MCP supports invoking multiple tools concurrently following a single semantic interpretation. Based on voice semantics, the AI populates parameters for both the `microbit_music` and `rgb_color` tools. The controller executes lighting changes and music playback in parallel, achieving synchronized sound and light interaction.

**Question 2: What does setting an MCP tool to non-blocking (false) signify?**

Answer: Non-blocking signifies that after a tool is called, the program does not wait for hardware actions to finish before continuing execution. It immediately returns to the main loop to continue listening for voice commands. Even during long musical playback, new voice commands can be received and processed.

### 5.5.6 Q&A

**Question 1: What does setting `blocking` to `true` mean for this MCP tool?**

Answer: A blocking setting of `true` means that after the AI calls the sensor tool, the program pauses and waits for the sensor to complete data collection. Only after receiving the return result does it continue executing subsequent code and return the data to the AI. This ensures that the AI reliably acquires sensor readings, which is suitable for query tools that require returned data.

**Question 2: Why must the sensor MCP have "data returned to AI module" enabled, whereas the previous sound, light, and dot matrix MCP tools did not require it?**

Answer: Dot matrix and sound-and-light MCP tools are execution tools where the AI sends commands to trigger hardware actions without needing return data. In contrast, sensor data collection is a query tool where the AI reads physical world measurements. Enabling data feedback is therefore essential for delivering sensor readings to the AI model for evaluation and voice responses.

- **MCP Configuration Analysis**

1. Tool name: `self.control.auto_drive_mode`

2. Tool description: Call this tool to select the automatic driving mode. The parameter `drive_mode` must be 0 to turn automatic driving off, 1 to turn following mode on, 2 to turn obstacle avoidance mode on, or 3 to turn colorful line tracking mode on. Only one mode can run at a time.

3. Return parameters: `[["drive_mode", "int", "0", "3"]]`

4. Block until tool execution completes: `false`

5. Data returned to AI module: `false`

6. Function: Receives the mode index from the AI to modify the robot global operating state. A background loop reads sensors and continuously regulates motors according to the selected mode. As a non-blocking tool, the AI can receive new voice commands after updating the mode.

### 5.8.5 Expansion

**Project 1: Audiovisual Cues for Mode Transitions**

Modify the program so that switching autonomous driving modes changes the ultrasonic LED colors and plays audio prompts. For example, illuminate blue for following mode, red for obstacle avoidance mode, and green for line-following mode, offering clear visual status distinction.

**Project 2: Hybrid Behavioral Logic Expansion**

Add boundary conditions to existing modes. While following tracks, enable ultrasonic detection concurrently. If obstacles are encountered, pause line following to execute avoidance maneuvers, resuming track navigation once obstacles clear.

### 5.8.6 Q&A

**Question 1: Can `drive_mode` be set to `1` and `2` simultaneously to enable following and obstacle avoidance at the same time?**

Answer: No. Only one autonomous driving mode can be enabled at a time. If two modes are enabled simultaneously, sensor control logic will conflict, causing abnormal movement of the robot car.

**Question 2: After obstacle avoidance mode is enabled, who controls the autonomous motion of the robot car, and does the AI still need to issue continuous motor commands?**

Answer: The autonomous motion of the robot car is controlled locally in real time by the micro:bit controller, which reads sensor data. The AI is only responsible for receiving voice commands and switching modes, without needing to continuously send motor motion commands.

## 5.9 App Image Transmission

>
> **This lesson introduces the image transmission feature. For app download instructions, overview details, and program analyses, refer to [4.15 App Control](./4.%20Nexbit%20AI%20Hands-on%20Projects.md#section-4-15).**

### 5.9.1 Image Transmission Overview

Image transmission is a feature that streams video in real time using the camera on the WonderLLM ESP32-S3 module. Upon power-up, the module creates a self-hosted Wi-Fi hotspot. Connecting a mobile phone to this hotspot enables the app to receive camera video feeds for remote viewing.

This feature serves robotic visual observation and scene monitoring, providing a foundation for AI vision projects such as visual recognition and object tracking. It allows direct observation of camera capture feeds to verify camera hardware wiring and image acquisition routines.

### 5.9.5 Q&A

**Question 1: Why is the module Wi-Fi hotspot not found after powering on following firmware flashing?**

Answer: 

1. Verify that the USB power supply is stable. 
2. Verify SPI MODE settings and switch between DIO and DOUT to reflash if necessary. 
3. Check for loose connections on the camera ribbon cable. 
4. Execute ERASE again before re-flashing firmware.

**Question 2: What causes a black screen without video in the app after successfully connecting to the hotspot?**

Answer: 

1. Confirm that the camera ribbon cable is oriented correctly. 
2. Ensure adequate power supply current to the module. 
3. Confirm that the flashed firmware is Image_transmission.bin rather than other project firmware. 
4. Restart the module and app, then reconnect to the hotspot.

**Question 3: How can video stutter and high latency be resolved?**

Answer: Minimize ambient wireless interference and ensure adequate module power supply. Avoid connecting multiple devices to the module hotspot simultaneously. Lower camera resolution parameters within the program to reduce data transmission volume.
